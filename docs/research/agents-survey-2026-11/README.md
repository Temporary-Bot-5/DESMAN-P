Оговорки. Многие цифры получены из отчётов самих вендоров и инвесторов. Результаты бенчмарков
агенты часто сообщают о себе сами. Закрытые продукты (Devin, Cursor, Manus, ChatGPT agent) описаны

предложения. Решения по ним не приняты.

## Главное за пять минут

1. **Самый большой спрос в 2026 году — на личного помощника, который живёт в мессенджере,
   работает по расписанию и помнит человека.** OpenClaw стал самым популярным репозиторием
   GitHub (~395 тыс. звёзд). Его ближайшая альтернатива, Hermes Agent от Nous Research (~267 тыс.),
   продаёт именно ту «эволюцию», которую люди чувствуют на себе: агент сам пишет себе навыки
   после сложных задач и сам ведёт свою память. У DESMAN уже есть то, чего у OpenClaw нет:
   устойчивые задачи, песочница по умолчанию, права, которые выдаёт только человек. Но у DESMAN
   нет каналов (Telegram и т. п.), задач по расписанию и сообщений по инициативе агента.
2. **Безопасность стала аргументом при выборе.** На ClawHub, публичном каталоге навыков OpenClaw,
   нашли сотни вредоносных навыков, а у самого OpenClaw была уязвимость с удалённым выполнением
   кода в один клик. Причина в том, что навык там — это «доверенный код» на машине пользователя.
   Подход DESMAN (bwrap+seccomp, защищённые файлы, подписанные релизы, изменения только с
   подтверждения человека) — то, чего этому рынку не хватает. Это стоит показывать, а не прятать.
3. **Люди хотят видеть и контролировать, а не отдавать агенту полную автономию.** По отзывам на G2,
   79% просят объяснений, ограничений и предупреждений перед рискованными действиями. Полную
   автономию хотят только 7%. Главная жалоба — сложная настройка. Среди тех, кто не пользуется
   ИИ, 47% не знают, как начать. Мастер настройки, чат и бесплатные ключи DESMAN бьют точно в эту цель.
4. **Ouroboros (Разжигаев и др., NeurIPS 2026) — ближайший к DESMAN самоулучшающийся агент.**
   Он эволюционирует из опыта: сбои, телеметрия, замечания ревью и жалобы людей превращаются в
   задачи на исправление самого себя. Коммит проходит через предпроверку, отпечаток диффа,
   ревью и проверку свежести. При этом агент вливает изменения сам, без решения человека по
   каждому из них. У DESMAN строже: каждое изменение применяет только человек. Это правильно и
   подтверждается инцидентами. Агент из Darwin Gödel Machine подделал лог прохождения тестов.
   Аудит самого Ouroboros снял засчитанный результат на Terminal-Bench. SWE-bench Verified
   оказался загрязнён, и OpenAI перестала по нему отчитываться.
5. **Самый действенный рычаг — не число агентов, а обвязка: контекст, проверка результата,
   интерфейс инструментов.** Это показывают контролируемые сравнения 2026 года (176 конфигураций),
   абляции SWE-agent и статья MAST о том, почему ломаются мультиагентные системы. Параллелить
   стоит только действительно независимые ветки работы. Мультиагентный режим Anthropic тратит
   примерно в 15 раз больше токенов. Cognition советует держать тесно связанную правку кода в
   одной траектории. Голосование крошечных моделей может даже ухудшать точность.
6. **Для бесплатных моделей работают каскады.** Сначала задачу берёт дешёвая модель, а при
   провале проверки — более сильная (FrugalGPT, lead/worker в Goose). Хорошо работает и пара
   «архитектор + исполнитель правок» (Aider). Сильная модель нужнее в роли оркестратора, чем в
   роли работников (исследование 2026 года на Qwen3).

## Что у DESMAN уже на уровне лучших

Это стоит знать, чтобы не переделывать готовое:

| Механизм у лидеров | У DESMAN |
|---|---|
| Песочница Codex: bubblewrap + seccomp-BPF; песочница Claude Code | `core/sandbox.py` + `core/seccomp.py`, без сети, квоты на рабочую папку |
| Activity в Temporal: намерение → результат, повтор без двойных побочных эффектов | `core/effects.py`, журнал вызовов, повтор отдаёт записанные результаты |
| Лизы, повторные попытки, эскалация к человеку (Temporal, Inngest) | `store.claim` с токеном, `retry.py` со стратегиями, входящие для человека |
| Чекпоинты и прерывания LangGraph | Чекпоинты подзадач, вытеснение срочными задачами, `resume` |
| Эволюция по схеме ADAS/DGM/GEPA: предложить → оценить → архив | Improvement Analyst → бенчмарк в изолированных worktree → `proposals apply`, только по решению человека |
| Компактизация истории (Claude Code, Codex, OpenHands) | `compaction.py` для чата |
| Маршрутизация по моделям с откатом на другие | `router.lineup`, Fallback, Backoff, ограничитель по провайдерам |
| Проверка работы другим участником сети (Bittensor, Proof of Sampling) | Перепроверка задания другим узлом в desman-global, подписанные записи |

## Чего не хватает: рекомендации по приоритету

Трудоёмкость: **S** — внутри одного модуля, **M** — несколько модулей, **L** — новая подсистема.
Источники каждой идеи указаны в частях 1–4.

### А. Направление «личный помощник» (ответ на спрос)

1. **Задачи по расписанию и повторяющиеся задачи; сообщения по инициативе DESMAN (M).** Это
   «heartbeat/cron» OpenClaw и cron Hermes: «каждое утро сводка», «раз в неделю проверь».
   В DESMAN это обычная задача с полем «когда» в SQLite, которую берёт worker. Права и
   подтверждения остаются прежними.
2. **Канал Telegram (L).** Чат DESMAN, доступный из мессенджера: вход только с привязанного
   аккаунта (как «pairing» в OpenClaw), входящие сообщения считаются недоверенными, окно
   подтверждения превращается в кнопки, которые строит код. Это самый прямой ответ на спрос, но
   и самая большая поверхность атаки. Нужен ADR.
3. **Навыки, выученные на опыте, с подтверждением человека (M).** Так работают Hermes, ACE,
   Zep Agent Skills, Voyager и Knowledge в Devin. После успешной задачи DESMAN предлагает
   «плейбук»: условия, шаги, проверку завершения, ссылки на трассы. Человек подтверждает, и
   плейбук становится узлом дерева знаний, который планировщик может выбрать. Различаем
   «сообщённый» и «проверенный» успех (идея Zep). Никакого автоматического принятия — у Zep оно
   включено по умолчанию, и именно так в агенты попадает мусор.
4. **Режим «объясни» и видимые объяснения (S).** 67% пользователей хотят, чтобы им объясняли, а
   не просто давали ответ. Сюда же — предупреждения перед рискованным шагом и понятный отчёт
   «что сделано и почему».

### Б. Эволюция (взять из Ouroboros, DGM, GEPA, AlphaEvolve)

5. **Кормить аналитика трассами и жалобами людей (S).** Идея «эволюции из опыта» Ouroboros и
   GEPA: повторяющийся сбой с точной причиной, проверенные примеры, ответственный компонент.
   Одно точечное изменение с ожидаемым наблюдаемым эффектом. Сюда же сообщения человека
   «это сработало плохо».
6. **Доказательства собирает только доверенный исполнитель (M).** Урок поддельных логов DGM:
   коды выхода, события политики и «задача действительно завершена» записывает только сам
   бенчмарк, вне того, что может менять кандидат. Прогон, не дошедший до конца из-за лимитов,
   показывается как «нет вывода», а не как проигрыш.
7. **Ступенчатая оценка, чтобы беречь квоту (M).** Подход AlphaEvolve и ShinkaEvolve: проверка
   схемы и отсев дубликатов, потом дешёвые smoke-задачи, и только потом парный прогон
   «текущее против кандидата» на одних и тех же моделях. Отдельный набор задач для
   подтверждения, который аналитик никогда не видит.
8. **Архив альтернатив по сильным сторонам (M).** Идея DGM и GEPA: хранить безопасные варианты,
   которые выигрывают на своём классе задач, даже если проигрывают в среднем, вместе с
   родословной. Так будущие предложения могут строиться не только от текущей версии.

### В. Качество работы на дешёвых моделях

9. **Каскад с резервом на эскалацию (M).** Дешёвая или локальная модель идёт первой. Сильная
   подключается при провале проверки, при застревании или противоречивых свидетельствах.
   Причину переключения пишем в журнал. Отдельно стоит попробовать пару Aider «архитектор
   описывает, дешёвая модель пишет правку» для подзадач с кодом.
10. **Дешёвое управление контекстом исполнителя (M).** Сначала правила, потом пересказ. Это
    лучший по эффективности вариант в исследовании 2026 года. Длинные выводы инструментов
    хранятся как артефакты по ID, в конце промпта — короткий чек-лист из DAG (`todo.md` у Manus),
    неудачные действия остаются видимыми.
11. **Проверяемые доказательства на рёбрах DAG (S).** У подзадачи уже есть
    `acceptance_criteria`. Не хватает того, чтобы планировщик указывал, *каким* будет
    доказательство (тест, цитата из источника, файл), а рецензент требовал именно его. Это
    закрывает категорию MAST «закончил раньше, чем выполнены критерии».
12. **Компактные интерфейсы инструментов (S).** Урок SWE-agent: важно не только какое действие
    даёт инструмент, но и что он возвращает. Короткие результаты поиска, структурированные
    ошибки, карта репозитория в духе Aider (символы и сигнатуры в пределах бюджета токенов).

### Г. Сеть и совместимость

13. **Выборочные перепроверки вместо проверки всего (M).** По мотивам Proof of Sampling и
    Bittensor: случайная выборка заданий на перепроверку, репутация узла по проверенным
    заданиям в каждом классе задач, проверяющие от независимых владельцев и провайдеров.
    Чувствительные задания не уходят в сеть по умолчанию.
14. **MCP — только через адаптер с белым списком (M).** Это крупнейшая экосистема инструментов
    в 2026 году, но и канал для атак через цепочку поставок. Начать с инструментов только для
    чтения. Всё, что что-то меняет, проходит через Workspace, Sandbox и окно подтверждения.
    A2A (v1.0, март 2026) — позже, для одного внешнего навыка исследования.
15. **Время у знаний (M).** Идея Graphiti: у узла дерева знаний и у заметки профиля есть дата
    наблюдения, срок действия и ссылка на то, что их заменило. Это нужно хотя бы для фактов о
    провайдерах, которые постоянно меняются.

## Чего не делать (подтверждено чужими ошибками)

- Открытый каталог навыков, где навык — это «доверенный код» (ClawHub). Если появится обмен
  навыками, то только подписанные, проверенные и выполняемые в песочнице.
- Автоматически принимать выученные навыки или правки памяти (по умолчанию у Zep, у mem0):
  ошибочный вывод модели остаётся советом навсегда.
- Доверять отчёту кандидата о собственном прогоне (DGM) или чужому бенчмарку без своей
  перепроверки (загрязнение SWE-bench Verified, ошибки проверяющих в Terminal-Bench 4.0).
- Мультиагентность ради мультиагентности. Параллельно — только независимые ветки, а синтез и
  общие записи держит один владелец.
- Голосование многих крошечных моделей как способ поднять качество: их ошибки скоррелированы.
- Ставить в зависимость заброшенные или закрываемые проекты. AutoGen архивирован, Roo Code
  закрыт в мае 2026. Gemini CLI перестал обслуживать личные подписки в июне 2026.

## В ROADMAP

Владелец решил взять всё (2026-11-27). В `ROADMAP.md` добавлены четыре фазы:

- **P — Личный помощник:** А1–А4 (расписание, сообщения по инициативе DESMAN, объяснения,
  Telegram), а также то, что люди используют чаще всего: голосовые сообщения, глубокое
  исследование, почта/календарь/файлы, браузер для страниц с JavaScript, время у знаний (Г15).
- **E — Эволюция из опыта:** Б5–Б8 и навыки из опыта (А3), уроки внутри задачи (Reflexion),
  поиск по форме плана (AFlow), стратегии самого аналитика (Promptbreeder, Hyperagents).
- **Q — Качество на бесплатных моделях:** В9–В12, критика плана до запуска, поиск FTS5,
  точки отката рабочей папки (Cline), замер того, когда делить работу.
- **N — Сеть и совместимость:** Г13–Г14, обмен навыками только с подписью, A2A,
  проверка улучшений другими узлами.

Начать без новых решений можно с E.1 (входы аналитика), Q.1 (доказательства на рёбрах DAG) и
P.1 (задачи по расписанию). Для P.4, P.7, P.8 и N.2 сначала нужен ADR.
