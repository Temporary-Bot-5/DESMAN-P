# DESMAN(P) — Roadmap

Цепочка небольших задач от текущего сырого прототипа до прототипа, который показывает
все 8 пунктов из раздела «What the prototype must demonstrate» в `PROJECT_PLAN.md`
(далее D1…D8).

Каждая задача — один PR: маленький, с тестом и понятным критерием «готово».
Порядок важен: следующая фаза опирается на предыдущую.

---

## Текущее состояние (аудит, 2026-10-26)

**Что есть:** SQLAlchemy-модели (Task/Subtask/Artifact/AuditLog), TaskStore с lease/checkpoint/retry,
шаблонный Planner, Executor и Reviewer с LLM и заглушками, ModelRouter с перебором 8 провайдеров,
CLI (`run/status/resume/list-tasks/audit/setup/config`). 15 тестов проходят, но только в режиме
заглушек: без LLM Executor возвращает фиктивный артефакт, а Reviewer принимает любой непустой.

**Критичные дефекты:**

| # | Проблема | Где |
|---|----------|-----|
| B1 | Если подзадача окончательно упала, зависимые остаются `PENDING` навсегда: цикл координатора не завершается | `coordinator.py`, `store.py` |
| B2 | Упавший посреди работы исполнитель не восстанавливается: `release_stale_leases` смотрит только `LEASED`, а не `RUNNING`/`CHECKPOINTED`; продления lease (heartbeat) нет. `resume` на такой задаче тоже зависает | `store.py:release_stale_leases` |
| B3 | `get_ready_subtasks` не учитывает зависимости, а при `limit=1` может бесконечно выбирать заблокированную подзадачу с высоким приоритетом. Получается deadlock | `store.py` |
| B4 | Результаты предыдущих подзадач не передаются следующим (`previous_artifacts="TBD"`), поэтому цепочка шагов фактически пустая | `planner.py`, `executor.py` |
| B5 | Выход за пределы workspace: LLM может вернуть `files: {"/etc/x": ...}` или `../../.bashrc`, а `run_code_sandboxed` не изолирован (есть сеть и вся ФС) | `executor.py` |
| B6 | `.env` нигде не загружается (`python-dotenv` объявлен, но не вызывается), поэтому роутер не видит ключи и всё тихо работает на заглушках | `cli.py` |
| B7 | Две несовместимые системы конфигурации: `desman setup` пишет `.env`, а `desman config` пишет `~/.config/desman/config.json` с другими именами переменных (`GOOGLE_API_KEY` вместо `GEMINI_API_KEY`, `CLOUDFLARE_API_TOKEN` вместо `CLOUDFLARE_API_KEY`). Ключи из `config.json` никто не читает | `config.py`, `cli.py` |
| B8 | Мастер настройки предлагает агентам root, доступ к ФС вне workspace, сеть и shell. Это прямо противоречит Security rules, к тому же эти разрешения нигде не применяются | `config.py` |
| B9 | Любая команда CLI сначала запускает интерактивный мастер, а `desman` без аргументов ждёт `input()`. Скриптовать и тестировать CLI нельзя | `cli.py`, `info.py` |

**Существенные недостатки:**

- Роутер: tenacity повторяет на *любой* ошибке, включая 401/400. Нет rate-limit, кэша, паузы при исчерпании квоты и лога вызовов моделей (спецификация требует хэш промпта и ответа, токены, задержку). `task_type` и `priority` игнорируются. Дефолтные модели устарели (`gemini-1.5-flash`, `llama-3.1-8b:free`). Для Cohere и Cloudflare указаны URL, которые не совместимы с OpenAI-форматом.
- Парсинг ответов LLM — голый `json.loads`. Бесплатные модели почти всегда оборачивают ответ в ```` ```json ````, поэтому каждый вызов будет падать.
- Ошибка исполнителя превращается в артефакт `type=error`, и эвристический ревьюер его *принимает*.
- `desman audit <task>` не показывает события подзадач: ищет `subtask` с `entity_id == task_id`. Вердикты ревьюера и вызовы моделей не логируются.
- `CHECKPOINTED` используется и как статус, и как данные. Явной таблицы переходов состояний нет.
- Приоритет задачи не передаётся подзадачам. Вытеснения (preemption), нескольких исполнителей и идемпотентности нет.
- Тулинг: в `pyproject` нет `aiosqlite` и `[project.scripts]` (команда `desman` не ставится). venv на Python 3.14 при цели ≥3.11. mypy: 9 ошибок, ruff: 7. Объявлен `anyio`, но используется `asyncio`. Модуль `__init__` называется «DESMAN-P+Human».
- Структура репозитория: внешний `DESMAN_Project/` — пустой git без коммитов. `DESMAN-P+Human/` — отдельная копия CLI-оболочки, которую последний коммит уже частично влил в `DESMAN-P`.

## Решения владельца (2026-10-26)

- Рабочее пространство и GitHub-репозиторий — `DESMAN-P`. `DESMAN_Project/` — просто папка проекта.
- `DESMAN-P+Human` — временное хранилище неудачных частей, **оставить как есть**.
- Ядро переписывается полностью; старая версия сохранена в коммите `3d10a5e`.
- Остаётся система конфигурации через `desman config` (`~/.config/desman/config.json`). `.env` и `desman setup` удалены. Тем самым B6 и B7 закрываются выбором, а не починкой.

## Фаза 1 — Надёжный одиночный цикл (Milestone 1 → D1, D3, D7)

- [ ] **1.1 State machine подзадачи.** Таблица допустимых переходов (`pending → ready → leased → running → review → done | retry | failed | blocked | needs_human`) и одна функция `transition()`, которая отвергает недопустимые переходы. Checkpoint — это данные, а не статус. *Готово:* тест на каждый переход.
- [ ] **1.2 Схема БД и миграции.** Таблицы tasks, subtasks, artifacts, audit_log, `schema_version`. SQLite в режиме WAL с `busy_timeout`. *Готово:* `desman init-db` идемпотентен.
- [ ] **1.3 Атомарный claim.** Один `UPDATE … WHERE status='ready' AND все deps done … RETURNING`, без «выбрать, потом проверить». Готовность зависимостей считается в запросе (устраняет B3). *Готово:* тест, в котором подзадача с высоким приоритетом заблокирована, а другая готова к выполнению.
- [ ] **1.4 Lease + heartbeat + восстановление.** Исполнитель продлевает lease; просроченные `leased/running` возвращаются в очередь с сохранённым checkpoint (устраняет B2). *Готово:* тест с промотанными часами.
- [ ] **1.5 Распространение отказов.** Окончательный `failed` переводит зависимые подзадачи в `blocked`, задача завершается со статусом `failed`, и цикл *всегда* заканчивается (устраняет B1). *Готово:* тест с таймаутом.
- [ ] **1.6 Контекст зависимостей.** Executor получает артефакты завершённых зависимостей, обрезанные по бюджету токенов (устраняет B4).
- [ ] **1.7 Path guard для workspace.** `resolve()`, запрет абсолютных путей, `..` и симлинков наружу, отдельный каталог на каждую задачу (устраняет B5, первая часть). *Готово:* набор вредоносных путей в тестах.
- [ ] **1.8 FakeLLM.** Детерминированный провайдер со скриптом ответов, включая мусор, таймауты и 429. На нём строятся все интеграционные тесты.
- [ ] **1.9 Полный аудит.** Каждый переход, вердикт ревьюера и checkpoint пишется в `audit_log` с `task_id`. `desman audit <task>` показывает всю историю (D7).
- [ ] **1.10 Команды задач.** Добавить `run`, `status`, `list`, `resume`, `audit`: неинтерактивные, с `--json`. Мастер запускается только из голого `desman` и из `desman config`.
- [ ] **1.11 Crash-тест.** Тест запускает `desman run` подпроцессом, убивает его `SIGKILL` посреди подзадачи, затем делает `desman resume`. Задача завершается, дублей артефактов нет (**D3**).

## Фаза 2 — Реальный LLM (→ D2)

- [ ] **2.1 Доработка конфигурации.** Pydantic-модель для `config.json` со `schema_version`. Роутер читает ключи из `ConfigManager`. `desman config` не должен затирать уже введённые ключи (сейчас при перенастройке теряются все, кроме введённых заново). Файл создаётся с правами `0600`. Привести имена переменных к именам провайдеров (`GOOGLE_API_KEY`, `CLOUDFLARE_API_TOKEN` + account id). Добавить `desman config show` с замаскированными ключами.
- [ ] **2.2 Один провайдер end-to-end.** OpenAI-совместимый клиент на httpx, актуальная бесплатная модель (OpenRouter `:free` или Groq). *Готово:* `desman run "..."` выполняется на настоящей модели.
- [ ] **2.3 Надёжный structured output.** Достаём JSON из ответа, включая ```` ```json ````-обёртки, валидируем Pydantic-схемой, при невалидном ответе делаем один «repair»-запрос с ошибкой валидации.
- [ ] **2.4 Лог вызовов моделей.** Таблица `model_calls`: провайдер, модель, хэш промпта, хэш ответа, токены, задержка, ошибка. `desman calls`.
- [ ] **2.5 Классификация ошибок.** 400/401/403 — без повторов. 429 и исчерпанная квота — пауза задачи (`paused_quota`) до указанного времени. 5xx и таймауты — backoff.
- [ ] **2.6 Кэш ответов** по хэшу (модель, промпт, параметры) — экономия квоты при retry и resume.
- [ ] **2.7 LLM-планировщик.** Цель превращается в граф подзадач (Pydantic-схема, проверка на DAG, лимит узлов). При сбое — шаблонный fallback (**D1**).
- [ ] **2.8 LLM-ревьюер.** Вердикт `accept | retry | escalate` с конкретными замечаниями, которые подставляются в повторную попытку. Артефакт `type=error` никогда не принимается.

## Фаза 3 — Инструменты и безопасность (→ D6)

- [ ] **3.1 Tool registry.** Инструменты объявляются со схемой аргументов и уровнем разрешений. Executor возвращает структурированные вызовы инструментов, а не пишет файлы напрямую.
- [ ] **3.2 Политика разрешений.** `permissions` из `config.json` (их задаёт человек в `desman config`) — верхняя граница. Поверх неё `policy.toml`: какие инструменты разрешены каким ролям. Агенты не могут менять ни то, ни другое. Каждый отказ пишется в аудит. `admin_rights` остаётся настраиваемым (для тестовых машин владельца): по умолчанию выключен, при включении — явное предупреждение при каждом запуске и запись в аудит каждого действия с повышенными правами (закрывает B8: права дают только человек и только явно).
- [ ] **3.3 Песочница для кода.** Подпроцесс через `bwrap` или `unshare`: без сети, ФС только workspace, rlimits, таймаут, очищенное окружение (устраняет B5, вторая часть).
- [ ] **3.4 Идемпотентность побочных эффектов.** У каждого side-effect-действия есть idempotency key, журнал `effects` с семантикой «записать намерение → выполнить → подтвердить». Повторный запуск не дублирует эффект (**D6**).

## Фаза 4 — Несколько исполнителей и приоритеты (→ D4, D5)

- [ ] **4.1 Процесс `desman worker`** отделён от координатора. N воркеров работают с одной SQLite.
- [ ] **4.2 Переназначение.** Тест: два воркера, один убит, его подзадачу доделывает второй (**D4**).
- [ ] **4.3 Глобальный приоритетный планировщик** по всем задачам, с защитой от голодания (aging).
- [ ] **4.4 Кооперативное вытеснение.** Появилась `critical`-задача: воркер с низкоприоритетной работой на ближайшем шаге сохраняет checkpoint и освобождает подзадачу. Решение записывается в аудит (**D5**).
- [ ] **4.5 Мульти-провайдерный роутинг.** Модели по ролям (planner, executor, reviewer), fallback-цепочка, rate limiter на провайдера в БД (token bucket переживает перезапуск).
- [ ] **4.6 Fault-injection-харнесс.** Случайные падения воркеров и провайдеров, повторяемые по seed.

## Фаза 5 — Человек и контролируемая эволюция (→ D8)

- [ ] **5.1 Очередь человека.** Статус `needs_human`, команды `desman inbox`, `approve <id>`, `reject <id> --note`. Сюда переезжает идея DESMAN-P+Human.
- [ ] **5.2 Метрики.** `desman stats`: успешность, число retry, вызовы и токены по ролям и провайдерам.
- [ ] **5.3 Защищённые файлы.** Список (`policy.toml`, ревьюер, тестовый харнесс, правила одобрения) с хэшами. Изменение без одобрения человека блокирует запуск.
- [ ] **5.4 Improvement Analyst.** По логам отказов предлагает изменение промпта, workflow или конфигурации в виде diff в `proposals/`. Сам ничего не применяет.
- [ ] **5.5 Оценка предложения.** Фиксированный бенчмарк-набор задач на FakeLLM и реальной модели. Предложение прогоняется в отдельном `git worktree` и сравнивается с текущей версией.
- [ ] **5.6 Применение и откат.** Применить можно только командой `desman proposals apply <id>` от человека: создаётся git-коммит или PR. Откат — `desman proposals revert <id>` (**D8**).
